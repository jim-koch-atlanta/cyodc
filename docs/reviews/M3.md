## Graph branching to support combat

Previously, the graph was a straight line:

```
START → dm → END
```

Now it forks on the `next_node` field:

```
START → dm ──(next_node == "combat")──▶ combat → END
          └──(next_node is None)──────▶ END
```

LangGraph essentially supports two ways of wiring up the connections between its graph nodes:

1. **Static edge** -- `add_edge("a", "b")` -- always go from `a` to `b`.
2. **Conditional edge** -- `add_conditional_edges("a", routing_fn, {...})` -- run a router function, and go wherever it returns.

In this case, we're using **conditional branching** in [graph.py](../../app/graph.py):

```py
    # The DM either ends the turn (exploration) or routes to combat (next_node).
    builder.add_conditional_edges("dm", route_from_dm, {"combat": "combat", END: END})
```

A function (`route_from_dm`) inspects state, and the edge dispatches based on the result.

This feels like a bypass to me, because the DM is doing zero work and just re-routes. However, **making the routing decision is the DM's work this turn.** The DM is checking the DB for an active fight and concluding that this is a combat round, so go do combat!

## Model tiering is itself a routing decision

The short-circuit above isn't just tidy — it's there for **cost**. The DM runs on Sonnet (smart, expensive); combat narration runs on Haiku (fast, cheap). We do **not** want to pay for Sonnet on every swing of a fight.

So the routing produces a "Sonnet at the seams, Haiku per round" shape:

- **Fight starts** → one Sonnet call (the DM interprets "attack the goblin" and calls `start_combat`).
- **Each round** → the DM short-circuits (zero model calls) and the combat node makes one Haiku call.
- **Fight ends** → there's no active encounter, so the DM resumes on Sonnet for the aftermath.

A 10-round fight costs roughly 1 Sonnet + 10 Haiku, not 11 Sonnet. This is invariant #5 (cost discipline) enforced by the graph shape rather than by a comment: _which model runs is part of the control flow._

## The `encounters` row is a state machine across stateless requests

A fight plays out over many HTTP turns, but each `graph.invoke()` is a single, stateless pass. So "which round am I on / how much HP does the monster have" can't live in the graph — it lives in the `encounters` row, and each turn the graph reconstructs where we are by reading it.

The row's **existence is the state**: a row present means "in a fight," absent means "exploring." That's exactly what the DM short-circuit checks. And because routing keys off the row's existence, deleting it (in [encounters.py](../../app/encounters.py)) both _ends the fight_ and, conveniently, makes the victory reward replay-safe — a re-run finds no row and awards nothing twice (the same idempotency idea as [Milestone 2](./M2.md)).

## Use seeds for reproducible state

Just like with the BSP algorithm from [Milestone 2](./M2.md), we want to be able to reproduce the combat after a disconnect. If we close the tab mid-fight, we should be able to resume later.

To allow that, we use a **seeded** random-number generator:

```py
def rng_for_round(seed: int, round_num: int) -> Random:
    return Random(seed ^ (round_num * 0x9E3779B9))
```

## For deterministic behavior, minimize use of the LLM.

Unlike the DM, the combat node needs to be as deterministic as possible. This is done using standard coding approaches:

1. The player types, "I attack the orc."
2. [classify_combat_action()](../../app/encounters.py) uses regex to classify the action — attack, flee, or use — defaulting to attack.
3. The engine uses standard dice-rolls to produce results:

```py
def roll_dice(notation: str, rng: Random, *, crit: bool = False) -> int:
    """Roll NdM+K. On a crit the dice (not the modifier) are rolled twice.

    Result is floored at 1 — a connecting hit always stings at least a little.
    """
    n, sides, mod = parse_dice(notation)
    dice = 2 * n if crit else n
    total = sum(rng.randint(1, sides) for _ in range(dice)) + mod
    return max(1, total)


def d20(rng: Random) -> int:
    return rng.randint(1, 20)
```

4. The lifecycle code ([encounters.py](../../app/encounters.py)) persists the results to the DB. (The engine itself stays pure — no DB, no LLM.)
5. _Now_ the combat node runs the LLM (Haiku) to narrate what already happened.

When the step's correctness matters, you should use the LLM only for narration and presentation, and you should use deterministic code for decisions.
