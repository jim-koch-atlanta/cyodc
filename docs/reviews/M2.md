# 2026-07-25: Review of Milestone 2 Code

This project is a vibe-coded effort, so I can gain familiarity with both agents and with LangGraph. Milestone 2 was defined as:

> SQLAlchemy schema from SPEC.md. DM gets typed tools: look, move, take, use, inventory. BSP `mapgen.py` with unit tests. Rooms exist and are hand-seeded (no worldgen agent yet). Fog-of-war tracked in `visibility`.

Here are some of my observations of the resulting generated code.

## The agent cannot **change** state directly

All state changes (item pickup & use, movement, etc) are performed by deterministic code and **tools**. See [game_tools.py](../../app/tools/game_tools.py).

As drawn by Claude:
```
player text ──▶ DM (LLM) ──proposes──▶ tool_call {name, args}
                   ▲                        │
                   │                   deterministic Python
              narrates ◀──tool result── validates + writes DB
```

Note that the LLM could still hallucinate a nonexistent item (i.e. It could narrate the sentence, "You have picked up the legendary sword.") This should be uncommon, since the narration is grounded in the tool result.

To reduce the likelihood of such hallucinations further, we could introduce a validator pass that cross-checks the narration against the state. If a mismatch is detected, the output could be regenerated.

## Tool calling is part of an **agent loop**

The [DM](../../app/nodes/dm.py) actually runs as part of a [tool_loop.py](../../app/nodes/tool_loop.py), which handles the LLM conversation + tool execution for one turn (one prompt from the user).

It caps the maximum number of tool-calling **rounds**, both for cost and to keep each turn bounded. On the final round it calls the LLM with `tools=None`, so the model can't request another tool and must narrate. That both terminates the loop and avoids ending on a dangling tool call (which would be an invalid conversation to resume later).

[tool_loop.py](../../app/nodes/tool_loop.py) will be used by other agents (combat, boss, NPC, etc) as well.

## The LLM is outside of the trust boundary (`InjectedToolArg`)

We provide the LLM with a collection of tools for it to use. However, we do not allow the model to supply the player ID or the database session handle.

Those parameters are defined in [game_tools.py](../../app/tools/game_tools.py) as **injected** arguments --

```py
@tool
def take(
    item: str,
    *,
    session: Annotated[Session, InjectedToolArg],
    player_id: Annotated[int, InjectedToolArg],
) -> str:
```

So instead, the LLM will only learn about the `item` parameter of the `take` tool. The parameters `session` and `player_id` are left out of the JSON schema presented to the LLM.

Then our agent loop injects the database session and player ID:

```py
        for call in tool_calls:
            result = _execute(call, session, player_id)
            produced.append(result)
            working.append(result)
```

## Actions require idempotency, because the orchestrator could replay a turn

LangGraph checkpoints after each node. If the process (the Python server) crashes after a tool wrote to the DB but before the checkpoint was saved, the node can run again — and the same tool executes a second time.

A crash doesn't re-run itself, though. Re-execution takes two things: the process **restarted** (by a supervisor — e.g. systemd, Kubernetes, or App Runner) **and** the turn **retried** (a client retry, a queue, or the user resubmitting). Only then does LangGraph resume from the last checkpoint and re-run the incomplete node. Locally today none of that is wired up, so a mid-turn crash simply loses the turn — this is a forward-looking concern for deployment (M7). But it's cheap to make the tools replay-safe now and expensive to retrofit later, so we do it now.

So to ensure the same item can't be acquired twice, the mutation is **gated on a one-time state transition**: `take` removes the item from the room *before* adding it to the inventory. On a replay, the item is already gone from the room, so the tool finds nothing there and does nothing.

Additionally, the [schema-guardian](../../.claude/agents/schema-guardian.md) has an idempotency rule to prefer **absolute values** (`gold = 150`) instead of **delta values** (`gold += 50`).

**Note**: This approach could have undesirable cosmetic effects. For example:

* The player could specify "take sword".
* The turn runs and the `take` commits.
* *After* it commits but *before* the checkpoint is saved, it crashes.
* On recovery the node re-runs. The `take` returns "nothing here".
* The LLM (DM) narrates, "There's no sword to take", even though the sword is in the player's inventory.

This sort of glitch would need to be addressed with an action ledger. This is beyond the scope of this vibe-coded project.

## The map is a Binary Space Partitioning (BSP) algorithm 

[Binary Space Partitioning](https://en.wikipedia.org/wiki/Binary_space_partitioning) recursively splits a space into smaller sub-spaces. The [mapgen.py](../../app/mapgen.py) code drops a room in each leaf, and it connects them with corridors.

Notice that it is **seeded and deterministic**. If the same seed value is used, it will produce the same dungeon. This conforms to one of the project invariants:

> **Deterministic code decides; LLMs narrate.** Dice rolls, hit/miss, damage, loot rolls, and map generation (BSP) are plain Python. Agents describe outcomes; they do not adjudicate them.
