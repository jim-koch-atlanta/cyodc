# 2026-07-25: Review of Milestone 1 Code

This project is a vibe-coded effort, so I can gain familiarity with both agents and with LangGraph. Milestone 1 was defined as:

> FastAPI app + minimal LangGraph graph (single DM node, SqliteSaver checkpointer) + bare React page with text pane and input. Player types anything, DM responds in character. No DB, no map, no combat. **Goal: prove the loop end-to-end.**

Here are some of my observations of the resulting generated code.

## Backend

### [config.py](../../app/config.py)

I wasn't familiar with `@property` or `@lru_cache`. Claude added both.

```py
@property
def resolved_llm_mode(self) -> Literal["anthropic", "stub"]:
```

What's the difference between a property and just a getter function? Not much, other than the implicit expectation that calling `config.resolved_llm_mode` has no side effects. So the property is basically implying C++ `const`-ness.

(**Caveat**: unlike C++ `const`, Python doesn't enforce the getter is side-effect-free — that's convention. It does enforce read-only access, since there's no setter.)

```py
@lru_cache
def get_settings() -> Settings:
```

This basically makes `get_settings()` a singleton. So the following is true:
```py
get_settings() is get_settings()
```

Neat.

### [state.py](../../app/state.py)

This contains the dungeon master (DM) state. Note the annotation:

```py
messages: Annotated[list[AnyMessage], add_messages]
```

The annotation is to identify the **reducer** that LangGraph should use when new messages are received. So rather than replacing `messages` each time a new `AnyMessage` is available, it will use the `add_messages` reducer, which will append.

### [llm.py](../../app/llm.py)

I was a little curious about why the agents' models are defined here in `MODEL_BY_ROLE`, rather than being defined in each agent. This seems like a contradiction of the Open-Closed Principle.

According to Claude, this centralization is intentional for auditability of usage. That makes sense, so I'm fine with it.

One thing worth noting is that it might make sense to combine the three `dict`s into a single one:

### [main.py](../../app/main.py)

"What's the deal with `graph.invoke()`?"

```py
result = graph.invoke({"messages": [HumanMessage(content=body.message)]}, config)
```

I was curious what is happening under the hood here. Keep in mind that `graph` is the compiled state machine from `[graph.py](../../app/graph.py)`. Right now it's just hard-coded to `START -> dm -> END`. However, it will eventually contain other nodes as well.

`invoke(input, config)` will run the state machine once from START to END, synchronously performing these commands:

1. Load the checkpoint for `config`'s `thread_id` (all prior messages for this session).
2. Merge input into that state via the reducers — our `{"messages": [HumanMessage(...)]}` gets appended by `add_messages` (see above).
3. Run the nodes along the edges — in M1 just `dm`, which returns a partial update `{"messages": [reply], "next_node": None}`; reducers merge it in.
4. Follow edges until `END`.
5. Write the new checkpoint (now containing our turn *and* the reply) — that's what makes resume work.
6. Return the final state dict.

So this:

```py
result = graph.invoke({"messages": [HumanMessage(content=body.message)]}, config)
reply  = message_text(result["messages"][-1])
```

means "append my message, run the DM, persist, and give me back the whole conversation".

## Frontend

The frontend is pretty basic, since this is essentially a text-based game (ala Zork). It does three things:

1. **When the page opens**, it asks the backend to start the story (or resume an existing story), and it shows the opening narration.
2. **When you type and hit send**, it ships the text to the backend, waits for the DM's reply, and pastes that reply at the bottom of the scroll.
3. **It remembers you** by stashing your session ID in the browser, so a page refresh picks up the same run instead of starting over.

### [App.jsx](../../frontend/src/App.jsx)

This is really the only interesting file. On load, it reads the saved session id (stored under `STORAGE_KEY`) from local storage:

```jsx
const stored = localStorage.getItem(STORAGE_KEY)
```

If an id is found, it asks the backend for that session's data. If there's no saved id — or the backend no longer has that session (it 404s) — it falls back to creating a new one.

When a new message is submitted, it will call the `sendTurn()` function from [api.js](../../frontend/src/api.js).

```jsx
const res = await sendTurn(sessionId, text)
setMessages((m) => [...m, { role: 'dm', content: res.reply }])
```

That is just making a POST call to the backend:

```js
const res = await fetch(`/api/session/${sessionId}/turn`, {
    method: 'POST',
    headers: JSON_HEADERS,
    body: JSON.stringify({ message }),
})
```

So overall, it's pretty straightforward.
